# FreeRTOS 开发流程

来源映射：原文第 1–10、19–29、31–44、48–56、62–70 节。任务和服务划分是可选方法，示例周期、优先级、阈值及重试次数不是通用要求。

## 从需求落到任务和接口

已有工程先追踪请求涉及的输入、活动入口、对象创建和结果消费者。新工程先明确 MCU/端口、内核版本、构建工具和 API 层。能从实际文件核实的信息不重复询问。

为重要功能确定以下契约，简单功能可以用短段落表达：

| 契约 | 必须能回答的问题 |
|---|---|
| 行为 | 什么输入触发，输出/反馈是什么，哪个状态允许执行？ |
| 时序 | 周期还是事件，最晚何时完成，超期如何处理？ |
| 数据 | 完整消息还是最新快照，单位/范围是什么，如何标记年龄与有效性？ |
| 所有权 | 哪个任务写业务状态，哪个任务操作外设，何时转移/归还缓冲区？ |
| 失败 | 创建、输入、传输、满队列、锁和处理失败分别如何返回或收敛？ |
| 结果 | 请求接受、处理完成和操作成功如何区分，谁消费结果？ |

能融入已有所有者的功能不必新增任务。新增任务需说明独立阻塞、响应期限或外设串行化带来的收益及栈/对象成本。优先级按执行与阻塞预算确定，避免“功能重要就设最高”。

## 选择 FreeRTOS 机制

交接机制按 [architecture.md](architecture.md) 的语义选择。不要为每个消息都加一个Mutex，也不要把Mutex当事件同步。Stream/Message Buffer等机制需核实当前版本支持及生产者/消费者限制。

保留工程的原生或封装 API 风格。原生句柄与 CMSIS 句柄的关系应通过实际封装核实，不能凭名称强行互转。原生 Tick 值使用对应类型和转换；CMSIS中的时间参数也要查其定义，不能当作毫秒直接传入。

周期任务使用当前版本提供的绝对周期接口或既有多周期调度器，初始化唤醒基准并确定超期策略。不同版本的 `vTaskDelayUntil()`、`xTaskDelayUntil()` 及封装接口不能直接假定可互换。短时间转Tick可能得到零，要根据期限处理量化误差，而不是无条件加一次零等待或把周期改成1Tick。

事件任务可在无请求时合法阻塞；若还承担周期职责，应把下一期限纳入等待时间。整体操作超时须覆盖底层调用、重试及锁等待，不能只给某个 API 设置 timeout。

## 实现完整模块

- 对外提供必要的初始化、请求/更新、读取或结果接口；内部上下文和缓冲区尽量私有，业务所有者由项目决定。
- 对命令用固定完整消息或有生命周期契约的缓冲区；对测量明确采样成功时间、质量和发布序号。请求序号和完成结果用于关联，错误不静默丢失。
- 初始化检查对象、任务和硬件创建结果，规定重复初始化行为及失败出口。静态创建与启动动态创建按资源预算选择；生命周期需覆盖停止/重启，不能留下仍访问已释放对象的任务或回调。
- Queue满时按消息性质决定拒绝、合并、覆盖或重试；结果通道也要处理满队列。只适合最新值的覆盖机制不能用于保留每条命令。
- 锁范围只覆盖必要共享访问；失败后不访问受保护对象，不跨耗时I/O持锁。临界区不调用会阻塞的API。SMP工程须核实端口同步语义，不能把单核关中断当作跨核保护。
- ISR使用允许的上下文API、零等待和正确唤醒方式，核对中断门限。DMA完成要闭合缓冲区归还；软件Timer Callback只做短且不阻塞的处理或事件投递。
- 状态机先检查事件、参数和允许状态，再执行动作；等待以分步状态和截止时间表达。严重故障与恢复策略按 [reliability.md](reliability.md) 实现，不复制自动重启危险输出的通用模板。
- 纯算法尽量与RTOS/HAL分开；平台入口使用现有驱动或窄适配接口。实际接口未知时先定位或明确待实现契约，不把臆造的HAL调用写成已经集成。

## 配置与集成

核对 `FreeRTOSConfig.h` 的相关开关、heap实现、栈单位、Tick频率、端口和中断设置。静态对象使用的存储区必须具有足够生命周期；Idle/Timer任务的内存回调是否需要由当前版本和配置确定。无需为小功能切换整个工程的内存分配方式。

将实际源码加入项目的构建入口，检查头文件、对象创建、启动顺序、生产者/消费者和处理结果是否都连接。把代码写入目录不等于已参与构建；不能只交付无调用者的任务函数或无消费者的队列。

对于CubeMX等生成工程，遵守项目对配置生成的职责和 `USER CODE` 边界，自定义业务优先放用户模块。配置与生成代码发生冲突时分别说明现状，按授权修正正确层；不通过直接修改生成区制造下一次生成就消失的配置。

裸机迁移先列出原有的ISR、轮询、延时、状态和外设访问，按路径迁移到任务/事件/状态机；保留协议、单位和业务时序契约。迁移一个可验证的功能链后再扩展，不一次替换整个产品架构。

## 验证与收尾

按 [verification.md](verification.md) 设计与改动相称的验证。故障修复应先能够触发原故障，再确认正常及异常路径；任务/交接变更核对所有权、对象配置、溢出、超时和资源峰值。

有工程构建命令则使用实际配置构建；缺少工具链或硬件时明确未验证项，不把主机替身测试当成固件运行证据。通过必要检查后进行一次变更自审，交付文件、行为、验证结果及实际限制，不为收尾扩大到无关重构。
