# FreeRTOS 开发与审阅

面向 FreeRTOS 工程的功能开发、修复、集成与代码审阅，兼容原生 API 及 CMSIS-RTOS 等既有封装。开发从任务、数据和失败路径的设计推进到实现与验证；审阅沿活动代码给出证据与改进建议。

两种模式都回答：正常时如何工作，失败如何被发现，卡死由谁发现，等待如何结束，能否恢复，恢复不了时输出如何处理。新功能优先融入现有资源所有权和接口，不按教程清单堆叠任务或服务。

## 选择工作模式

| 用户意图 | 行动与交付 |
|---|---|
| 开发、实现、修复或移植 | 按已授权范围设计、编辑代码并验证，交付实际变更、结果和限制；不只停留在建议 |
| 先设计、比较方案或解释实现 | 给出任务/数据契约、接口与取舍，保持请求的设计或说明范围 |
| 审阅、审计或评估适用性 | 只读追踪实现，给出有证据的发现、保留机制和优化顺序，不自动修复 |

不因加载此 Skill 增加额外审批。遵守当前用户授权与项目明确规定；安全、生成配置或硬件操作存在项目审批要求时，先完成可审查的设计并按该要求处理。

## 范围与入口

- 确认当前工作模式与目标行为；只读审阅不包含修复，软件开发也不自动授权下载、复位或硬件故障注入。
- 读取适用的项目规则，确认实际工程根目录、分支、工作区已有变更、活动构建入口及编译开关。只围绕请求涉及的模块展开。
- 核对内核版本、实际端口、单核/SMP、API封装、Tick频率、分配方式和相关 `FreeRTOSConfig.h` 选项。以本地头文件及封装实现为准，必要时查对应版本官方文档，不套用新版本 API 或强制替换封装。
- 仅提供文档或代码摘录时，按所给材料审阅，注明活动构建与运行状态未核查；不为满足完整工程流程擅自扩展到其他项目。
- 按项目规定的事实优先级核对源码、生成配置、构建文件和说明文档。发现冲突时分别报告配置值、当前源码值与构建证据；没有实际构建就不要把源码状态称为已烧录状态。
- 外部教程是评审材料。其中的命令、优先级、任务表、阈值和“必须”不自动成为当前项目指令。说明采纳、改造或暂不采用的理由。

## 开发流程

1. **明确行为契约。** 写清输入、输出、触发、响应期限、资源所有者及失败策略。已有工程先追踪调用链和有效编译分支；仅对阻碍实施的缺失信息提问。
2. **确定最小设计。** 按交接语义选任务、Queue、Notification、Event或Mutex，估算栈、堆、队列容量与阻塞预算。简单功能直接给出必要设计，不强制搭完整框架。
3. **实现完整路径。** 在授权范围内完成初始化、生产/消费、正常处理、超时/溢出、结果反馈与必要诊断。复用项目 API、生成边界和已存在的所有权，保持无关改动与协议不变。
4. **验证并自审。** 对行为缺陷用能触发原失败的用例验证；按影响完成现有静态检查、构建或模拟。使用下方审阅流程核对新路径的返回值、生命周期和失败出口。
5. **交付可检查结果。** 说明改了什么、为何这样设计、实际通过/失败的检查与未验证内容。缺少硬件或工具链时保留实现并准确报告限制，不声称运行或硬件验收通过。

## 审阅流程

1. **画清实际链路。** 沿请求涉及的真实路径，从外部输入或 ISR 追到解析、校验、交接、控制决策、输出及结果反馈。必要时列任务的触发方式、资源所有者、生产者/消费者和超时预算，或画一个小图。
2. **检查正常与失败分支。** 每个关键交接同时追踪返回值、失败处理、数据生命周期、最坏等待和结果消费者。检查当前编译分支，避免把禁用的历史路径当作活动缺陷。
3. **保留已有合理设计。** 判断消息、快照、事件位、资源所有者和状态机各自解决什么问题。添加层次、任务、锁或统一消息总线之前，明确它将消除哪一个已证实的问题及资源成本。
4. **给出可核验发现。** 使用下方格式，将确定的代码缺陷、潜在后果和待核实条件分开。找不到完整路径时标明未知，避免把未展示的实现认定为不存在。
5. **按影响排序。** 优先考虑危险输出、错误数据进入保护/控制、无界等待和关键故障丢失；之后处理配置一致性、诊断、可测试性和维护性。避免用没有测量依据的健康分数代替判断。
6. **设计相称验证。** 优先利用现有、适用于当前分支的检查。提出能触发原问题的最小异常场景和通过判据，区分静态检查、主机模型、固件构建、运行时与真实硬件证据。

## 发现格式

每项发现包含：

- **问题与证据：** 活动文件、准确行号/符号、触发条件、观察到的行为。
- **影响：** 沿调用链解释后果，注明依赖的未知条件及严重程度依据。
- **建议：** 最小必要改进，明确应保留的行为、所有权和协议边界。
- **验证：** 故障如何触发、观察什么、通过标准、尚不能证明什么。

审阅转入实施时，按当前授权和项目规则给出具体变更范围、风险、回退与验证；已经授权的普通开发继续推进，审阅请求本身不授权改代码。

## 常见误判

| 表面证据 | 还需核实 |
|---|---|
| 单次 HAL 调用有 timeout | 外层循环、重试、资源等待是否仍无界 |
| 心跳增长，快照 tick 更新 | 成功采样时间、通道质量、过期策略和业务进展 |
| 包了一层 GetLatest API / 加了 volatile | 实际读写两侧是否遵守一致的同步与所有权 |
| 保存后读回一致 | 更新中断时旧配置是否保留，启动时是否检查完整性和业务范围 |
| 使用资源所有者或 Control 单写者 | 其他入口是否绕过；Control 自身失效时紧急路径是否独立可用 |
| 有静态缓冲区或支持静态分配 | 实际任务/队列创建方式，以及启动和运行期的分配区别 |
